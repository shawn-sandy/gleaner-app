The **astro-basics** visual direction is seven colour tokens, three type roles, and one structural rule that ties
colour to interactivity. These tokens are the public styling contract for projects that import this package, so the
names and their meanings are stable and every one of them is overridable from a consumer stylesheet. The homepage
adds a scoped [Gleaner brand layer](#the-gleaner-brand-layer) on top, which never shares a colour with them.

## The Rule: Colour Marks Hydration

The direction is one idea specific to Astro rather than to websites in general.

Astro ships static HTML and withholds JavaScript. The palette says the same thing the framework does: static content
renders in ink on paper, and the accent, `--island`, appears **only** where something is interactive - links, buttons,
focus rings, the interactive-specimen badge. Nothing decorative carries it.

<Aside type="caution" title="This is machine-checked, not a preference">
  `e2e/homepage-design-direction.spec.ts` walks the rendered homepage and asserts that no
  non-interactive element computes to the accent colour. Using `--island` for a decorative border, a
  heading, a hairline or a card surface fails that test. Treat it as a structural constraint, the
  same way you would treat a type error.
</Aside>

<CardGrid>
  <Card title="Ink for what is static" icon="document">

    `--paper-sunk`. If a visitor cannot operate it, it does not get the accent.
  </Card>
  <Card title="Island for what responds" icon="rocket">
    Links, buttons, focus rings and the specimen badge use `--island` and `--island-bg`. The accent

## The Seven Direction Tokens

Defined in `src/styles/_design-tokens.scss` and consumed in `src/styles/_base.scss`.

| Token          | Light     | Dark      | Role                                                           |
| -------------- | --------- | --------- | -------------------------------------------------------------- |
| `--ink`        | `#101418` | `#e8eaed` | Primary text; the default `color` on `body`                    |
| `--ink-soft`   | `#5a6472` | `#99a2ad` | Secondary text: decks, eyebrows, labels, captions, inline code |
| `--paper`      | `#fcfcfd` | `#0d1014` | Page background                                                |
| `--paper-sunk` | `#f1f3f5` | `#151a20` | Recessed surfaces: the header band, card backgrounds           |
| `--island`     | `#0b6070` | `#6bb9c9` | The accent. Interactive only                                   |
| `--island-bg`  | `#e6f2f6` | `#102a33` | Accent wash behind interactive affordances and `::selection`   |
| `--rule`       | `#dde1e6` | `#262c33` | Hairlines and dividers                                         |

The accent is a deep petrol — a low-chroma blue-green. It is deliberately neither Tailwind sky-500 nor the
violet/indigo family that generated palettes converge on, so the page does not read as a framework default. Low chroma
is the point: the accent sits beside ink as a second voice rather than shouting over it, and it darkens cleanly under
the `color-mix` hover states instead of going muddy. Every pair clears WCAG 2.1 Level AA. Measured against the running
page rather than estimated: in light, ink on paper is 18.04:1, ink-soft on paper 5.85:1, island on paper 7.01:1, and the
lowest pair of all — ink-soft on paper-sunk — 5.39:1; in dark, island on paper is 8.54:1 and the lowest pair — again
ink-soft on paper-sunk — is 6.77:1. `e2e/home-accessibility.spec.ts` asserts the 4.5:1 AA floor against the tokens the
page actually resolves, so no repoint can drop a pair below AA without failing the build. The exact figures above are
not themselves asserted — they record the current budget, and re-measuring is part of changing a token.

### How the themes are applied

Both themes are SCSS mixins applied through three scopes:

```scss
:root {
  @include direction-light;
}

@media (prefers-color-scheme: dark) {
  :root {
    @include direction-dark;
  }

  @include direction-dark-surfaces;
}

:root[data-theme='dark'] {
  @include direction-dark;
  @include direction-dark-surfaces;
}

:root[data-theme='light'] {
  @include direction-light;
}
```

`:root[data-theme]` carries specificity (0,2,0) against the media query's (0,1,0), so an explicit toggle beats the OS
preference regardless of source order. Starlight already stamps that attribute on these docs routes.

<Aside type="tip" title="Why the dark block paints elements">
  Redefining `:root` variables alone is not enough. @fpkit/acss resolves its surface colour from a token this project
  never declares and hardcodes `whitesmoke` on the header band, so `direction-dark-surfaces` has to reach `body`,
  `body > header`, `body [data-card]` and `::selection` directly. A dark block that only sets variables cannot change
  a pixel.
</Aside>

## Which Surfaces the Aliases Paint

Two component aliases sat in the token file with zero consumers, which is why every painted surface inherited
@fpkit/acss defaults. Both now point at direction tokens and both have real painted consumers.

<Tabs>
  <TabItem label="--card-background">
    Aliased to `var(--paper-sunk)` and painted by `body [data-card]`, plus the same selector inside the dark scopes.

    `[data-card]` is the attribute @fpkit/acss puts on its `Card` root, so the alias reaches:

    - `Card.astro` everywhere it renders, including the six homepage feature cards and the hero specimen
    - the promoted-tier specimens in `FeatureCards.astro`
    - `Featured.astro`
    - `DashboardCard` and anything else composed on the @fpkit/acss `Card`

    ```scss
    body [data-card] {
      background-color: var(--card-background);
    }
    ```

    The selector is scoped through `body` on purpose. The vendor rule is (0,1,0); `body [data-card]` is (0,1,1) and
    wins on specificity rather than on whichever stylesheet the bundler emits last. It also leaves the card's own
    header strip alone.

  </TabItem>

  <TabItem label="--header-background">
    Aliased to `var(--paper-sunk)` and painted by `body > header`, which covers the shared `Header.astro` band on every
    route and the `HomeHero.astro` band on the homepage.

    ```scss
    body > header {
      background-color: var(--header-background);
    }
    ```

    The child combinator is load-bearing twice over: (0,0,2) beats the vendor's (0,0,1), and it cannot reach a nested
    `header` inside a card.

    A third header token, `--header-deck-font-size`, sizes the deck paragraph under the shared header heading. It is a
    fluid `clamp()` on a shallower slope than the heading's own clamp, so the two separate as the viewport grows
    instead of converging.

  </TabItem>
</Tabs>

## The Three Type Roles

One typeface used to render across every heading, paragraph, link and button, so elements differed only by size. Three
roles is the smallest set that reads as deliberate.

| Role        | Token                   | Applies to                                                        | Treatment                                  |
| ----------- | ----------------------- | ----------------------------------------------------------------- | ------------------------------------------ |
| **Display** | `--font-family-display` | `h1` through `h6`                                                 | Inter 600, negative tracking               |
| **Body**    | `--font-family-sans`    | `body`, `p`, `li`, everything inheriting from `body`              | Plus Jakarta Sans 400                      |
| **Mono**    | `--font-family-mono`    | `code`, `kbd`, `samp`, `[data-ui="eyebrow"]`, `[data-ui="label"]` | Uppercase, `0.12em` tracking, `--ink-soft` |

- **Display covers every heading level.** `h1` through `h6` all render at weight 600, which is the single weight the
  self-hosted woff2 ships - so the full range costs no additional font request.
- **Casing is not part of the role.** `text-transform: capitalize` stays on `h1`-`h3`, which are titles. `h4`-`h6` are
  used for UI labels - the contact form renders its error summary as an `h6` - and capitalizing a sentence would
  produce "Please Correct The Following Errors".
- **Tracking is negative on display.** `-0.015em` on `h1`-`h6`, tightened to `-0.02em` on `h1`.
- **The display stack falls back through the system sans**, so a failed font request degrades to a sans rather
  than to a serif.
- **Body is declared on `body`, not `html`.** @fpkit/acss sets `font-family` on `html`, which is why one face used to
  render everywhere. Declaring the body role on `body` beats that by inheritance and leaves the headings free.
- **Mono is opt-in for anything that is not code.** Code semantics get it by element; everything else opts in through
  a data attribute, so an eyebrow is a deliberate choice at the call site rather than a selector guessing at class names.

The display face is self-hosted: a latin-subset, single-weight `inter-600.woff2` in `public/fonts/`, declared
with `font-display: swap` and preloaded from `src/layouts/Base.astro`. No CDN and exactly one font request.

### Using the mono role

```astro
<p data-ui="eyebrow">30+ components / built for Claude Code</p>
<figcaption data-ui="label">Rendered</figcaption>
```

Both attributes resolve to the mono family, `--ink-soft`, `0.75rem`, `0.12em` tracking and uppercase.

## Overriding the Tokens as a Consumer

Projects importing this package get the components, and the components read these custom properties at runtime.
Nothing is compiled in, so a consumer rebrands the kit by redefining properties - no fork, no SCSS build, no component
edits.

Two rules make an override stick:

1. **Load your sheet after the kit's stylesheet.** Every override below has the same specificity as the kit's own
   declaration, so source order decides the winner.
2. **Override all three scopes.** The kit sets the tokens in `:root`, in `@media (prefers-color-scheme: dark) :root`,
   and in `:root[data-theme='dark']` and `:root[data-theme='light']`. Redefining only `:root` leaves the dark path on
   the kit's values.

<Aside type="danger" title="Overriding only :root is the common mistake">
  It looks correct in light mode and silently keeps the kit's palette the moment the visitor's OS is
  set to dark, or the moment a theme toggle stamps `data-theme` on the root element.
</Aside>

<Tabs>
  <TabItem label="Colour">
    ```css
    /* your-app/src/styles/brand.css - imported after the kit's index.css */

    :root,
    :root[data-theme='light'] {
      --ink: #12100e;
      --ink-soft: #6b6257;
      --paper: #fffdf9;
      --paper-sunk: #f5f0e6;
      --island: #b4531a;
      --island-bg: #fdeee2;
      --rule: #e4dbcb;
    }

    @media (prefers-color-scheme: dark) {
      :root {
        --ink: #f4efe7;
        --ink-soft: #a89a88;
        --paper: #14110d;
        --paper-sunk: #1d1913;
        --island: #ff9a5c;
        --island-bg: #2a1a10;
        --rule: #2e2820;
      }
    }

    :root[data-theme='dark'] {
      --ink: #f4efe7;
      --ink-soft: #a89a88;
      --paper: #14110d;
      --paper-sunk: #1d1913;
      --island: #ff9a5c;
      --island-bg: #2a1a10;
      --rule: #2e2820;
    }
    ```

    You do not need to re-declare the painted rules. `body`, `body > header`, `body [data-card]` and `::selection` all
    resolve through `var()`, so redefining the variables repaints every surface that consumes them.

  </TabItem>

  <TabItem label="Type">
    ```css
    :root {
      /* Keep a fallback chain. The kit's @font-face rule and the Base.astro
         preload still reference the bundled Inter file. */
      --font-family-display: 'Söhne Breit', ui-sans-serif, system-ui, sans-serif;
      --font-family-sans: 'Söhne', ui-sans-serif, system-ui, sans-serif;
      --font-family-mono: 'Berkeley Mono', ui-monospace, monospace;
    }
    ```
  </TabItem>

  <TabItem label="Component aliases">
    The alias layer is a second, narrower override surface. Re-point an alias when a surface should diverge from the
    direction rather than follow it.

    ```css
    :root {
      --card-background: var(--paper); /* flush cards instead of recessed */
      --header-background: transparent; /* no header band at all */
      --header-deck-font-size: clamp(1rem, 0.8vw + 0.85rem, 1.375rem);
      --card-radius: 0;
    }
    ```

  </TabItem>
</Tabs>

### What an override must not break

`--island` is the only token bound to a structural rule. If you re-point it, keep it on interactive surfaces only.
Applying your accent to a heading, a decorative border or a static card background reintroduces exactly the ambiguity
the direction removes - and it fails `e2e/homepage-design-direction.spec.ts` if you run this project's suite.

## The Gleaner Brand Layer

The site's Gleaner rebrand arrives as a scoped layer over the direction above, not a replacement. The homepage hero, the
feature section below it, the Quick install and Requirements cards and the blog section's posts paint in the Gleaner
logo's own colours - an evergreen disc and a copper string - and set their display moments in the wordmark's typeface.
The Quick install, Requirements and blog headings, and every other site route outside these Starlight docs, still paint with the seven direction tokens.
The two layers never share a colour, which is what keeps the accent audit meaningful.

`DESIGN.md` at the repository root is the full record, with every colour role, contrast figure and component
measurement. This section covers the contract a contributor has to keep.

### The scoped palette

The brand colours live in `src/styles/gleaner-palette.css` as custom properties on any element marked `data-gleaner`,
in two families:

- **`--g-*`** paints the sections' own surfaces, type and controls: `--g-ground`, `--g-ink`, `--g-muted`,
  `--g-headline`, the `--g-button-*` install button, `--g-link`, the `--g-code-*` install panel, and the feature
  section's `--g-band`, `--g-card`, `--g-chip` and `--g-marker-*`.
- **`--glean-*`** paints the string components: `--glean-string`, the white ask card (`--glean-surface`,
  `--glean-border`, `--glean-ink`), the copper "you" label (`--glean-you`), Gleaner's reply (`--glean-reply`), the
  `--glean-mark-*` highlight for captured content, and the evergreen saved clip (`--glean-clip-*`).

| Property          | Light     | Dark      | Role                                                                    |
| ----------------- | --------- | --------- | ----------------------------------------------------------------------- |
| `--g-ground`      | `#f5f8f6` | `#0e1d1a` | Hero band background                                                    |
| `--g-ink`         | `#12302b` | `#e4efeb` | Hero body and card text                                                 |
| `--g-muted`       | `#4a615c` | `#a3bab3` | Fine print, labels, post dates                                          |
| `--g-headline`    | `#185c53` | `#9ed9c8` | Evergreen: headlines, skill names, the brand focus outline              |
| `--g-button-bg`   | `#185c53` | `#9ed9c8` | Install button fill, under `--g-button-ink` (`#fff` / `#0e1d1a`)        |
| `--g-band`        | `#fff`    | `#0e1d1a` | Feature section background                                              |
| `--g-card`        | `#f5f8f6` | `#152b27` | Skill cards, the sample clip, the Quick install and Requirements cards  |
| `--g-chip`        | `#e3efeb` | `#234240` | Command chips and the install cards' code                               |
| `--glean-string`  | `#c46b43` | `#d98a62` | The copper string. Graphic only                                         |
| `--glean-you`     | `#9a4a26` | `#eba67f` | The "you" label, the one place copper is text                           |
| `--glean-clip-bg` | `#185c53` | `#185c53` | The saved clip and the blog's latest-post card. Does not flip with dark |

The stylesheet sets the palette in the same three theming scopes as the direction tokens:

```css
/* src/styles/gleaner-palette.css, abridged */
[data-gleaner] {
  --g-headline: #185c53;
}

@media (prefers-color-scheme: dark) {
  :root:not([data-theme='light']) [data-gleaner] {
    --g-headline: #9ed9c8;
  }
}

:root[data-theme='dark'] [data-gleaner] {
  --g-headline: #9ed9c8;
}
```

The light values sit on `[data-gleaner]` itself, and the OS-dark block excludes `data-theme='light'` with `:not()`, so
a light toggle needs no block of its own. Neither dark block sets `--glean-clip-*`: the saved clip and the blog's
latest-post card keep their evergreen fill in both themes.

Two loading rules follow from the palette living in one shared file:

- **Each component that sets `data-gleaner` imports the stylesheet itself** - `HomeHero`, `HomeSectionNav`,
  `HomeFeatures`, `HomeInstall`, `HomeRequirements`, `HomeBlog` and `BackToTop` - and the browser loads it once.
- **Components that only read the palette carry fallbacks.** `GleanPart`, `SavedClip` and `SkillCard` give every
  property they read a light-theme fallback, so they still render outside a `data-gleaner` element. `CopyCommand`
  falls back to the inherited colour.

<Aside type="note" title="Why the palette is not in _design-tokens.scss">
  The committed `src/styles/index.css` is out of step with its SCSS source, so recompiling it to add
  global tokens would ship unrelated changes. Keeping the palette in its own stylesheet is a
  recorded compromise. Promote it into the token file only alongside a deliberate recompile and
  review of `index.css`.
</Aside>

### The Separate Hue Rule

No Gleaner colour equals `--island`, in either theme. The accent audit in `e2e/homepage-design-direction.spec.ts` walks
every element on the homepage in light and dark, and flags any non-interactive one whose computed colour, background,
painted border or outline equals the resolved `--island`. The Gleaner sections paint headlines, links and the
saved clip in evergreen, and the audit still passes because evergreen is its own hue: in OKLCH, `#185c53` sits at hue
182 against Harbour Teal's 215, and the dark `#9ed9c8` at 175 against `#6bb9c9` at 212.

<Aside type="caution" title="Never tune a Gleaner colour toward --island">
  The audit is an exact match, so it would not catch a near-miss. An evergreen nudged a few degrees
  toward Harbour Teal passes the test while making the accent ambiguous again. Keep the brand layer
  on its own evergreen and copper hues, never reuse `--island` inside it, and re-run the audit in
  both themes after changing either palette.
</Aside>

Contrast for the hero pairs, computed with the WCAG formula from the shipped hex values:

| Pair                                   | Light   | Dark    |
| -------------------------------------- | ------- | ------- |
| `--g-headline` on `--g-ground`         | 7.29:1  | 10.93:1 |
| `--g-ink` on `--g-ground`              | 13.24:1 | 14.76:1 |
| `--g-muted` on `--g-ground`            | 6.22:1  | 8.46:1  |
| Install button label on its fill       | 7.79:1  | 10.93:1 |
| `--glean-string` on `--g-ground` (3:1) | 3.55:1  | 6.42:1  |

`e2e/home-accessibility.spec.ts` asserts the 4.5:1 floor for the direction tokens only, so these figures are a recorded
budget rather than an assertion. Re-measure when a value changes. `DESIGN.md` records the feature section, install
card and blog pairs.

### Brand type: Plus Jakarta Sans

Plus Jakarta Sans does two jobs from one variable woff2, `public/fonts/plus-jakarta-sans-wght.woff2`, which covers
weights 200 to 800 under the SIL OFL 1.1. At 400 it is the body face, `--font-family-sans`, so bold body text -
links, labels, `strong` - renders in it at 600-700 like any body face. Its display use, as the Gleaner brand face at
600-800, is reserved for brand moments:

| Brand moment                                  | Weight    | Component                   |
| --------------------------------------------- | --------- | --------------------------- |
| Navigation brand, drawn into its SVG wordmark | 600       | `Navigation`                |
| Hero headline                                 | 800       | `HomeHero`                  |
| Hero install button                           | 650       | `HomeHero`                  |
| Saved clip title                              | 800       | `SavedClip`                 |
| Feature section `h2` and `h3`, skill names    | 800       | `HomeFeatures`, `SkillCard` |
| Quick install card names                      | 800       | `HomeInstall`               |
| Requirements card names                       | 800       | `HomeRequirements`          |
| Blog latest-post title, earlier-post titles   | 800 / 700 | `HomeBlog`                  |

Those are the only headings it sets. Page headings on every other site route outside the Starlight docs stay on the
Inter 600 display face, and labels
stay mono. The brand roles part from body copy by weight, size and colour rather than by family, so the three type roles
still hold, and the brand face costs no font request beyond the body face: the `@font-face` is declared once in
`src/styles/_design-tokens.scss` and the file is preloaded from `src/layouts/Base.astro` beside the Inter file.

The components name the face directly, ahead of a fallback variable - for example
`font-family: 'Plus Jakarta Sans', var(--font-family-display, sans-serif)` - so overriding `--font-family-sans` changes
body copy but leaves the brand moments on Plus Jakarta Sans.

### The brand components

Every brand component reads its colours from the `--g-*` and `--glean-*` properties, so it renders correctly only
inside a `data-gleaner` element or on its light fallbacks alone.

| Component          | `data-gleaner`                           | Used in                                                    | What it is                                                                                 |
| ------------------ | ---------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `HomeHero`         | On its `header`                          | `src/pages/index.astro`, header slot                       | The hero band: logo, headline, install button and panel, and the example thread            |
| `HomeSectionNav`   | On its root `div`                        | `src/pages/index.astro`, header slot after `HomeHero`      | The "On this page" strip: one numbered row on a desktop, a grid of tiles on a phone        |
| `BackToTop`        | On its wrapper `div`                     | `src/layouts/Base.astro`, every route                      | The "Back to top" tile pinned to the bottom-right corner of every page                     |
| `GleanPart`        | Reads it                                 | `HomeHero`'s example thread                                | One plain-language ask on the copper string, with any captured content and Gleaner's reply |
| `SavedClip`        | Reads it                                 | The last item of the same thread                           | The evergreen clip the string ties off in, at the logo's knot                              |
| `HomeFeatures`     | On its `section`                         | `src/pages/index.astro`, featured slot                     | The feature band: skill cards, the sample clip's anatomy and the save destinations         |
| `SkillCard`        | Reads it                                 | `HomeFeatures`                                             | One skill: its name, `/gleaner:` command chip, description and "Things to say"             |
| `HomeInstall`      | On its card grid, not its heading        | `src/pages/index.astro`, main content                      | The Claude and ChatGPT Quick install cards                                                 |
| `HomeRequirements` | On its cards and footer, not its heading | `src/pages/index.astro`, main content                      | The Claude and ChatGPT Requirements cards, each split into required and optional           |
| `HomeBlog`         | On its posts, not its heading            | `src/pages/index.astro`, main content                      | The newest post on an evergreen card and up to three earlier rows                          |
| `CopyCommand`      | Reads it, else inherits                  | `HomeHero`'s install panel and `HomeInstall`'s Claude card | One install command with a button that copies it                                           |

A few behaviours carry the design:

- **The string is one line.** Each `GleanPart` draws its copper string from its top through the gap to the next item,
  so consecutive parts read as one unbroken line, and `SavedClip` ties it off in the knot from `gleaner-symbol.svg`.
  The string and its wraps are `aria-hidden`; the asks and replies carry the meaning.
- **One command per `CopyCommand`.** Claude Code takes a single slash command per message, so a button that copied two
  lines would paste both into one prompt and run neither. Each button's accessible name is "Copy " plus its command,
  and the result is announced through a `role="status"` region that is in the markup from the start.
- **Headings stay outside the scope.** `HomeInstall`, `HomeRequirements` and `HomeBlog` mark their cards and posts, not
  their headings, so "Quick install", "Requirements" and "From the blog" keep the site's own heading face, weight and
  colour.
- **No published post, no section.** `HomeBlog` leaves itself out entirely when the `posts` collection has nothing
  published.

### The hero logo's scroll fade

The hero logo, `gleaner-symbol.svg`, fades out and shrinks to 80% over the first logo-height of scroll as it rises
toward the pinned navigation. It is the system's only scroll-linked animation:

```css
.home-hero .home-hero__logo {
  --hero-logo-size: clamp(7rem, 25vw, 12.5rem);
}

@supports (animation-timeline: scroll()) and (animation-range: 0 1px) {
  @media (prefers-reduced-motion: no-preference) {
    .home-hero .home-hero__logo {
      animation: home-hero-logo-fade linear both;
      animation-range: 0 var(--hero-logo-size);
      animation-timeline: scroll();
    }
  }
}

@keyframes home-hero-logo-fade {
  to {
    opacity: 0;
    scale: 0.8;
  }
}
```

- **Reduced motion keeps it opaque and full size.** The animation applies only under
  `prefers-reduced-motion: no-preference`.
- **It scales with `scale`, not `transform`.** The individual property composes with any transform the logo picks up
  later instead of replacing it.
- **The `@supports` test checks the range as well as the timeline.** Firefox 144 with scroll-driven animations switched
  on supports `animation-timeline: scroll()` but not `animation-range`, and would spread the fade over the whole page.
- **Everywhere else the logo stays opaque and full size.** A browser without scroll-driven animations never sees the
  animation, so the fade is an enhancement rather than a dependency.

### Overriding the Gleaner palette

The brand components are this site's homepage, not package exports - `src/components/index.ts` does not export them -
so the Gleaner layer is not part of the consumer contract the direction tokens are. A fork, or a page in this project
that reskins the brand components, overrides `--g-*` and `--glean-*` the same way the direction tokens are overridden:
in all three scopes, with the stylesheet's own selectors, loaded after it. The dark selectors carry (0,3,0), so a sheet
that redefines only `[data-gleaner]` loses to them in dark mode.

```css
/* your-overrides.css - loaded after gleaner-palette.css */
[data-gleaner] {
  --g-headline: #7a3b2e;
  --g-button-bg: #7a3b2e;
}

@media (prefers-color-scheme: dark) {
  :root:not([data-theme='light']) [data-gleaner] {
    --g-headline: #f0c2b4;
    --g-button-bg: #f0c2b4;
  }
}

:root[data-theme='dark'] [data-gleaner] {
  --g-headline: #f0c2b4;
  --g-button-bg: #f0c2b4;
}
```

### What a Gleaner override must not break

- **The Separate Hue Rule.** No value may equal `--island` in either theme, or drift toward it. This binds in both
  directions: re-pointing `--island` in a consumer stylesheet has to clear the Gleaner values too. Run the accent audit
  in light and dark after either change.
- **Copper is a graphic.** `--glean-string` is measured against the 3:1 graphics threshold, not the 4.5:1 text floor.
  `--glean-you` is the only copper that sets text; never use the string colour for type.
- **`--glean-clip-*` does not flip.** The saved clip and the blog's latest-post card keep their light values in dark
  mode, and the "Read the post" button inverts them (a `--glean-clip-ink` fill under a `--glean-clip-bg` label). A
  replacement has to read on its own fill in both themes.
- **The hero ratio.** `e2e/homepage-design-direction.spec.ts` reads the hero `h1` against the paragraph after it and
  requires a display-to-deck ratio of 3.0 or more at 1280px and 390px. The hero derives its deck from the headline size
  to hold that, so resizing one means checking the other.
- **The type-role probe.** The same spec reads the display role from the first heading outside `[data-gleaner]`, which
  today is "Quick install". Moving `data-gleaner` onto the Quick install, Requirements or blog heading changes which
  heading that test reads.
- **The recorded contrast.** The figures above are a budget, and no test asserts them. Re-measure every pair a changed
  value touches. If you change the defaults in `gleaner-palette.css` rather than overriding them, update the matching
  light fallbacks in the components that read them.
